### Added

#### `Executor`, `ProgressTailer`, and output validation

Runs ffmpeg, watches it, and judges what it produced. Three decisions here are
load-bearing, each from something that went wrong in production:

- **argv, never a shell.** Media filenames routinely contain quotes, semicolons
  and dollar signs. As arguments they are inert; interpolated into a shell they
  are commands.
- **Progress via a file, not a pipe.** Read from a pipe, a reader that falls
  behind fills the buffer and blocks ffmpeg itself — the encode stalls because
  nobody drained a status line. stderr is drained on its own thread for the same
  reason.
- **Duration from the last packet PTS, never the container header.** Measured
  on real files: an 8-second source truncated to a fifth reports a last-packet
  PTS of 1.5s against the original's 7.9s — while the MKV header reports no
  duration at all. A header-derived duration cannot catch this.

`ProgressTailer` reads `out_time_ms` as **microseconds**, which is what ffmpeg
has always written despite the name; treating it as milliseconds understates
progress a thousandfold and makes a healthy encode look stalled.

An unprobeable output validates as a *failure*, not an error — the 1 KB
AV1/NVDEC artefact must be rejected, not reported as a tooling problem a caller
might retry past.

Integration tests drive real ffmpeg: a complete output passes, a truncated one
is rejected, and `ValidationGate::Size` is asserted never to have been reached —
a truncated file is always smaller, so a size-first gate accepts exactly the
outputs that destroyed the media.
